# flow-layout

The user values the visual readability of OutSystems flows. A flow created through the ModelAPI has **no positions** (every node sits on the same spot) and no labels, so it is unreadable until this skill is applied. **Apply it to every action you create or change, before merging.** Do not ask; it is the standing preference.

## The rules
1. **Grid layout.** Columns are 2286 units apart, rows 1829. Start is at (2743, 1371). The main path runs **straight down**; the True branch of an `If` goes **right**; a ForEach loop body goes right and the code after the loop continues below; exception-handler flows go in their own lane to the right of the main flow (row 1).
2. **Nothing overlaps and no connector crosses a node.** When a connector would cross a node (typical: a loop going back up, a merge far away), do not leave it: route it through **dummy Assign nodes** (empty assign, label `Loop back` or `Route`) placed at every turn of a path through free cells. Later loop-backs to the same target merge into the first route instead of opening a new one.
3. **One Assign and one End per branch.** Never let several branches share the same tail. Repeat the Assign (same assignments) and give each branch its own End, placed next to its `If` (Assign then End side by side), so lines stay short and clear.
4. **Every Assign, If, ForEach and Message node has a label that says what it does**, readable in the flow without opening it: `Set output: Reply, IsDone`, `Mask email`, `Stale reply?`, `Build log entry (Error)`. Never leave the default `Assign` or an empty label. Ifs are phrased as the question they ask. (The API gives no label to Start, End, Aggregate, JavaScript, Exception Handler or the nodes that call actions: those keep their own names, so name them well when you create them.)
5. **Comments are linked.** Create each comment with `CreateNode<ICommentNode>()` and set `.Text`, then link it with `comment.CreateConnector(node)` to **every node it explains** (one comment can link to several). A comment about the **whole action** has no link and goes **on top, a little aside from the main flow** (x = Start x + 1700, y = 250). Comments say *why* and the non-obvious rule (guardrail, order that matters, known limit), not what the node name already says. Keep them to one or two sentences.
6. **Never delete or move what someone else wrote.** The pass deletes only its own dummies (empty assigns labelled `Loop back` / `Route`) and its own comments (text equal to one of the Spec comments). Original comments stay.
7. **Prove it** (together with rule 8: no input, output or local without a Description). Run the checker (`check-flow.cs`) after merging and report its numbers. Target: 0 crossing, 0 unreachable, 0 open-ended, 0 overlapping, 0 unlabelled assign/if, and unlinked comments only for whole-action overviews.

8. **Every action has a Description, and so does every input, output and local variable.** Action description (`action.Description = "..."`, works on server, screen and data actions): one or two sentences saying what the action does, its guardrail or limit, and who calls it; helpers say which action they serve; mocks say they are mocks. Never describe an action from its name alone: read its nodes and comments first.

   **The same applies to data objects you create:** every structure, entity and site property gets a Description, and **every attribute of every structure and entity** too (`structure.Description`, `attribute.Description`; one sentence: meaning, unit or time zone, allowed values, empty = what, personal data flag, never-secret notes). Site properties: say what an empty value means. These live in the same change, not a later pass.

   Parameters and locals: One sentence saying what the value means (unit, time zone, who fills it, empty = default, what a flag does), not the name repeated. Set it when you create the variable (`p.Description = "..."`; works on `InputParameters`, `OutputParameters`, `LocalVariables` of server and screen actions, and on block inputs). Write it from what the code actually does: read the assignments before describing a local you did not design. Do not overwrite descriptions written by someone else. Verify with a read-back: `Description` is `null` (not `""`) when empty, so test `string.IsNullOrEmpty`-style with `p.Description == null || p.Description == ""`. Data actions have no `InputParameters` in the API: describe their variables by hand.

## How to apply (every time)
1. Build or edit the logic with `applyModelApiCode` as usual, but give every node a **name** where the API allows (`CreateNode<IExecuteServerActionNode>("FindEmailStart")`, aggregates, JavaScript nodes) because comments and labels are matched by name or by assignment text.
2. Write a `Spec(actionName)` table (see the example in `polish-flow.cs`): rows `{"L", "kind:key", "label"}` for labels and `{"C", "comment text", "kind:key", ...}` for comments (no anchors = whole-action comment). Anchor kinds: `start`, `assign` (substring of `var = value; ...`, or `^exact`), `if` (condition substring), `foreach` (record list substring), `exec` (node name, server or client call), `agg`, `js`, `handler`, `raise`. An anchor matches **every** node that fits (two summary assigns get one comment).
3. Run `polish-flow.cs` (replace `Spec` and the action list at the bottom). It does, in order: clean up its own earlier output, duplicate shared Assign/End tails, lay out the grid, route crossing connectors through dummies, write labels, write linked comments. It works on `IAction`, which covers **server actions and screen/client actions**. Data actions (`IDataAction`) are a different interface: place their few nodes by hand with the same grid constants (`X(c) = 2743 + c*2286`, `Y(r) = 1371 + r*1829`), then label and comment them the same way.
4. `omlMerge`, then run `check-flow.cs` and fix what it reports. Re-running the pass is safe (it cleans up its own output first), but **it re-lays out the whole action**: if the user moved nodes by hand, say so before re-running and preserve their positions (use the checker only).
5. Mention the layout result in the change record (objects, check numbers).

## ModelAPI facts this relies on (verified)
- `OutSystems.Model.Logic.IAction` is the common type of server and screen actions: `.Nodes`, `.CreateNode<T>()`, `.OutputParameters`. Data actions are `IDataAction` (no common base): same `.Nodes` / `.CreateNode<T>()`.
- Reaching the block's actions: `eSpace.MobileFlows.Named("MainFlow").Children.OfType<OutSystems.Model.UI.Mobile.IMobileBlock>().Named("<block>").ScreenActions.Named("<action>")` (also `.DataActions`).
- Node members: every `IActionNode` has `HorizontalPosition` / `VerticalPosition` / `Delete()`. `Label` exists only on Assign, If, ForEach and Message. Targets: Start / Assign / Exec (server and client) / JavaScript / Message / Aggregate / ExceptionHandler `.Target`; If `.TrueTarget` and `.FalseTarget`; ForEach `.Target` (after the loop) and `.CycleTarget` (the body). `ICommentNode`: `.Text`, `.Connectors` (each has `.Delete()`), `CreateConnector(node)`; it has no target and no size. Assignments: `.Assignments`, each with `.Variable.Text`, `.Value.Text`, `.SetValue(...)`. `If`: `.Condition.Text`. ForEach: `.RecordList.Text`.
- The sandbox rejects the words `System`, `Process`, `Console` anywhere in the code, and rejects imports other than `OutSystems.Model`. So: no `Dictionary` / `List<T>` / `Func<>` by name (use arrays, `var`, LINQ results and local functions), and name helpers `Polish`, not `Process`.
- A `.ToList()` snapshot of `act.Nodes` is needed before deleting or creating nodes in a loop.
- `omlReset` first if the user edited the module in Service Studio since your last call (otherwise your snapshot is stale and `omlMerge` says the path does not match the working copy). `omlMerge` can run for minutes or hang: after a timeout, check the model before re-applying.
- **Read-only diagnostics trick:** `eSpace.ServerActions.Named("REPORT" + text)` always throws, and the exception message carries `text` back without saving anything. `check-flow.cs` uses it.
- Dummy assigns validate with no warning.
- New entities with many attributes raise the "Update Behavior" scalability warning. Fix: `entity.UpdateBehavior = (OutSystems.Model.Enumerations.UpdateEntityBehaviorType)1;` (value 1 = Optimized = "Changed Attributes" in Service Studio; 0 = Full). Imports: `OutSystems.Model`.
- Descriptions are `null` when empty, so test `== null || == ""`.
