# crud-wrapper-pattern

OutSystems entities should never be exposed with public write access to consumer modules. Doing so violates encapsulation, breaks business rule enforcement, and creates database integrity risks.

Apply this pattern to every business entity in Core Services (`_CS`) modules.

---

## 1. Golden Rule: Read-Only Entities

When an entity is marked `Public = Yes`, you must **always** set:
```text
Expose Read Only = Yes
```
Consumer modules can query the entity via Aggregates for read operations, but **cannot** call `Create<Entity>`, `Update<Entity>`, or `Delete<Entity>` directly. All modifications must flow through public Core CRUD wrapper actions.

---

## 2. Mandatory Audit Attributes

Every business entity must include standard audit tracking attributes:

| Attribute | Data Type | Mandatory | Default Value | Description |
| :--- | :--- | :---: | :---: | :--- |
| `CreatedBy` | `User Identifier` | Yes | `NullIdentifier()` | User who created the record |
| `CreatedOn` | `Date Time` | Yes | `CurrDateTime()` | Timestamp of record creation |
| `UpdatedBy` | `User Identifier` | Yes | `NullIdentifier()` | User who last updated the record |
| `UpdatedOn` | `Date Time` | Yes | `CurrDateTime()` | Timestamp of last modification |
| `IsActive` | `Boolean` | Yes | `True` | Used for soft-delete pattern |

---

## 3. Standard CRUD Actions Suite

For each entity (e.g. `Customer`), create public Server Actions in the `CRUD` folder:

### A. `<Entity>_Create`
* **Inputs**: `<Entity>` record (or DTO structure) **without** the autogenerated identifier.
* **Outputs**: `Id` (Entity Identifier), `IsSuccess` (Boolean), `ErrorMessage` (Text).
* **Flow logic**:
  1. Validate mandatory fields and business rules (e.g. valid tax ID, unique email).
  2. Set audit fields:
     * `Entity.CreatedBy = GetUserId()`
     * `Entity.CreatedOn = CurrDateTime()`
     * `Entity.UpdatedBy = GetUserId()`
     * `Entity.UpdatedOn = CurrDateTime()`
     * `Entity.IsActive = True`
  3. Call native `Create<Entity>` action.
  4. Assign output `Id = Create<Entity>.Id`, `IsSuccess = True`.

### B. `<Entity>_Update`
* **Inputs**: `<Entity>` record containing the `Id`.
* **Outputs**: `IsSuccess` (Boolean), `ErrorMessage` (Text).
* **Flow logic**:
  1. Validate that the record exists via an Aggregate.
  2. If not found, set `IsSuccess = False`, `ErrorMessage = "Record not found"`, and exit (or raise `NotFoundException`).
  3. Validate business update rules.
  4. Preserve original `CreatedBy` and `CreatedOn`.
  5. Update modification audit fields:
     * `Entity.UpdatedBy = GetUserId()`
     * `Entity.UpdatedOn = CurrDateTime()`
  6. Call native `Update<Entity>` action.
  7. Set `IsSuccess = True`.

### C. `<Entity>_Get` / `<Entity>_GetForUpdate`
* **Inputs**: `Id` (Entity Identifier).
* **Outputs**: `<Entity>` record, `IsFound` (Boolean).
* **Flow logic**:
  1. Query entity by `Id`.
  2. For `<Entity>_GetForUpdate`, perform aggregate/query with lock to prevent race conditions during concurrent modifications.
  3. Assign output record and set `IsFound = Aggregate.List.Count > 0`.

### D. `<Entity>_Delete`
* **Inputs**: `Id` (Entity Identifier), optional `IsHardDelete` (Boolean, default: `False`).
* **Flow logic**:
  * **Soft Delete (Standard)**: Call `<Entity>_Update` setting `IsActive = False`, `UpdatedBy = GetUserId()`, `UpdatedOn = CurrDateTime()`.
  * **Hard Delete (If explicitly allowed)**: Verify referential integrity / foreign keys first, then call `Delete<Entity>`.

---

## 4. Error Handling and Transactions

* If a validation fails, do not write to the database. Set `IsSuccess = False` with a human-readable `ErrorMessage`.
* In critical multi-step operations (e.g. creating an Order and OrderItems), if an error occurs, ensure you trigger `Abort Transaction` before returning an error output to rollback partial writes.
